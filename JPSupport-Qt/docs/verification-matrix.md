# JPSupport-Qt 実機検証記録

各環境・条件での動作確認状況を記録します。「4点セット」とは以下を指します。

1. 変換キー2種（`Ctrl+Space`、`半角/全角`）
2. 候補ウィンドウのカーソル追随
3. 文節移動（`←→`、`Shift+←→`）
4. 変換対象文節の強調表示（テーマの選択色の背景と文字＋下線）、他の文節は破線の下線
   （2026-10-07に変更。旧: 変換対象文節の水色文字＋水色太線下線表示。それ以前の確認結果は旧基準によるもの。）

これはIME全般の公式規格ではなく、Qtが公式に要求する最低要件（`QInputMethodEvent`のTextFormat/Cursor属性の解釈）と、Mozc等の主要な日本語IMEで一般的な操作慣習（文節下線・`Shift+←→`での区切り変更）を踏まえて、本プロジェクトの検証用に整理した項目です。

## Fcitx5デーモンの不調による見かけ上の不具合(2026-08-19判明)

2026-08-19の再検証時、クリーンにビルドしたLazarusで変換キー(`半角/全角`・`Ctrl+Space`)が一切反応せず、Fcitx5インジケーターも無反応という症状に遭遇しました。長時間かけてPascal側のイベントディスパッチ、C++バインディング層(`qwidget_c.cpp`等)、フォーカス同期(`focusObject`)まで踏み込んで調査しましたが、いずれも正常であることが確認され、コード側に原因は見つかりませんでした。

最終的に、原因は**Fcitx5デーモン自体の不調**でした。長時間起動しっぱなしのデーモンが不安定な内部状態に陥っており、`fcitx5-remote`コマンドが`Failed to get reply.`を返す状態になっていました。この状態では、JPSupport-Qtで作ったLazarusだけでなく、**Gedit(GTK3)のような無関係のアプリでも同様に日本語入力が完全に反応しなくなっていました**。

```bash
fcitx5-remote -e   # デーモン終了
fcitx5 -d          # デーモン再起動
```

これでLazarus・Gedit双方とも即座に正常動作するようになりました。コード側の変更は一切不要でした。

**教訓**: 「変換キーに無反応、インジケーターも無反応」という症状に遭遇した場合、Pascal/C++側の深い技術調査に入る前に、まず(1)無関係な別アプリでも同様に無反応か確認し、(2)Fcitx5デーモンの再起動を試すこと。詳細な手順は[`docs/troubleshooting.md`](troubleshooting.md)の「4.1 IME自体がまったく反応しない」を参照。

## IBusによる入力メソッド乗っ取り(2026-08-30判明、上記「Fcitx5デーモンの不調」の実態)

上記`lazarus_4_6`の検証時、変換キー・インジケーターとも無反応という、2026-08-19判明分と同様の症状に再び遭遇しました。今回、`fcitx5-diagnose`による診断と、症状発生中のプロセス確認を通じて、**より根本的な原因**が判明しました。

`fcitx5-diagnose`実行時、Fcitx5プロセス自体が消えており、代わりに`ibus-daemon`・`ibus-x11 --kill-daemon`等のIBus関連プロセスがログイン時(セッション開始時刻)から動いていることを確認。`~/.xinputrc`を確認したところ、以下の記載がありました。

```
run_im ibus
```

つまり、**Ubuntu標準の入力メソッド管理(`im-config`)が、Fcitx5ではなくIBusを起動する設定になっていた**ことが原因でした。IBus側の`ibus-x11 --kill-daemon`は、既に登録されている入力メソッド(Fcitx5)を積極的に終了させる仕様であるため、ログインするたびにIBusがFcitx5から入力メソッドの座を奪っていた、と考えられます。2026-08-19時点では「Fcitx5デーモン自体の不調」と結論づけましたが、より正確には「IBusに乗っ取られていた」可能性が高いです。

**恒久的な対処:**

```bash
im-config -n fcitx5
```

実行後、ログアウト・ログインし直すことで、`~/.xinputrc`が`run_im fcitx5`に変わり、以後Fcitx5デーモンの手動再起動なしで安定して動作することを確認しました。

**教訓(2026-08-19分の更新)**: 「変換キー・インジケーターとも無反応」という症状に遭遇した場合、Fcitx5デーモンの再起動を試す前に、まず`cat ~/.xinputrc`で`run_im`の対象を確認すること。`ibus`になっていれば、`im-config -n fcitx5`→再ログインが恒久的な解決策になる。デーモン再起動は、あくまで再ログインするまでの一時しのぎに過ぎない可能性がある。詳細な手順は[`docs/troubleshooting.md`](troubleshooting.md)の「4.1 IME自体がまったく反応しない」を参照。

## IBus環境での既知の制限

複数の環境(RasPi4/Debian12、VMware x86_64/Ubuntu22.04)での検証を通じ、IBus + Mozcの組み合わせに、Fcitx5にはない、以下の制限があることを確認しました。

1. **`Ctrl+Space`が効かない**：Lazarus IDE自体が、`Ctrl+Space`を「コード補完」のデフォルトショートカットとしてハードコードしているため(`components/synedit/syncompletion.pas`)、IBusのトリガーキーとして機能しません。**`半角/全角`キーは影響を受けず、正常に動作します。** これはJPSupport-QtやIBus自体の不具合ではなく、Lazarus IDEのキーバインド設定に起因するものです。
2. **候補ウィンドウが画面左上に固定される**：`SlotInputMethodQuery`は正しく呼ばれ、正しい座標をQtに返していることをログで確認済みですが、それでも候補ウィンドウの位置には反映されません。当初はIBus自身のQt統合(`QIBusPlatformInputContext`)側の制約と考えていましたが、2026-09-06のaarch64(Raspberry Pi 4)環境での再検証により、**Qt本体側の既知の上流バグ([ibus/ibus#2391](https://github.com/ibus/ibus/issues/2391))であることを特定**しました。いずれにせよJPSupport-Qt側での修正は困難です。
3. **プリエディット文字列の重複表示**(2026-07-24修正済み)：IBus + Mozcは、同一の文字範囲に対して複数の`TextFormat`属性を個別に送ってくることがあり、これを単純にセグメントとして積み上げると、変換中の文字列が重複して表示される不具合がありました。同一範囲のセグメントをマージする処理を追加し、修正済みです。

## 今後の検証方針

- Qt6はコード差分がQt5とほぼ皆無であることを確認済みのため、代表的な1環境で成功を確認できれば、他環境への横展開は基本的に問題ないと判断する
- 「4点セット」のうち、Fcitx5環境では全項目が確認できているが、IBus環境では上記の制限により、`Ctrl+Space`と候補ウィンドウ追随の2項目が構造的に満たせない。これは今後もIBus利用時の既知の制限として案内する
